DOCUMENT: HTTP caching

§0 Types of caches
S0 In the HTTP Caching spec, there are two main types of caches: private caches and shared caches.

§1 Private caches
S1 A private cache is a cache tied to a specific client — typically a browser cache.
S2 Since the stored response is not shared with other clients, a private cache can store a personalized response for that user.
S3 On the other hand, if personalized contents are stored in a cache other than a private cache, then other users may be able to retrieve those contents — which may cause unintentional information leakage.
S4 If a response contains personalized content and you want to store the response only in the private cache, you must specify a private directive.
S5 http
S6 Personalized contents are usually controlled by cookies, but the presence of a cookie does not always indicate that it is private, and thus a cookie alone does not make the response private.

§2 Shared cache
S7 The shared cache is located between the client and the server and can store responses that can be shared among users.
S8 And shared caches can be further sub-classified into proxy caches and managed caches.

§3 Proxy caches
S9 In addition to the function of access control, some proxies implement caching to reduce traffic out of the network.
S10 This is usually not managed by the service developer, so it must be controlled by appropriate HTTP headers and so on.
S11 However, in the past, outdated proxy-cache implementations — such as implementations that do not properly understand the HTTP Caching standard — have often caused problems for developers.
S12 Kitchen-sink headers like the following are used to try to work around "old and not updated proxy cache" implementations that do not understand current HTTP Caching spec directives like no-store.
S13 http
S14 However, in recent years, as HTTPS has become more common and client/server communication has become encrypted, proxy caches in the path can only tunnel a response and can't behave as a cache, in many cases.
S15 So in that scenario, there is no need to worry about outdated proxy cache implementations that cannot even see the response.
S16 On the other hand, if a TLS bridge proxy decrypts all communications in a person-in-the-middle manner by installing a certificate from a CA (certificate authority) managed by the organization on the PC, and performs access control, etc. — it is possible to see the contents of the response and cache it.
S17 However, since CT (certificate transparency) has become widespread in recent years, and some browsers only allow certificates issued with an SCT (signed certificate timestamp), this method requires the application of an enterprise policy.
S18 In such a controlled environment, there is no need to worry about the proxy cache being "out of date and not updated".

§4 Managed caches
S19 Managed caches are explicitly deployed by service developers to offload the origin server and to deliver content efficiently.
S20 Examples include reverse proxies, CDNs, and service workers in combination with the Cache API.
S21 The characteristics of managed caches vary depending on the product deployed.
S22 In most cases, you can control the cache's behavior through the Cache-Control header and your own configuration files or dashboards.
S23 For example, the HTTP Caching specification essentially does not define a way to explicitly delete a cache — but with a managed cache, the stored response can be deleted at any time through dashboard operations, API calls, restarts, and so on.
S24 That allows for a more proactive caching strategy.
S25 It is also possible to ignore the standard HTTP Caching spec protocols in favor of explicit manipulation.
S26 For example, the following can be specified to opt-out of a private cache or proxy cache, while using your own strategy to cache only in a managed cache.
S27 http
S28 For example, Varnish Cache uses VCL (Varnish Configuration Language, a type of DSL) logic to handle cache storage, while service workers in combination with the Cache API allow you to create that logic in JavaScript.
S29 That means if a managed cache intentionally ignores a no-store directive, there is no need to perceive it as being "non-compliant" with the standard.
S30 What you should do is, avoid using kitchen-sink headers, but carefully read the documentation of whatever managed-cache mechanism you're using, and ensure you're controlling the cache properly in the ways provided by the mechanism you've chosen to use.
S31 Note that some CDNs provide their own headers that are effective only for that CDN (for example, Surrogate-Control).
S32 Currently, work is underway to define a CDN-Cache-Control header to standardize those.

S41 Heuristic caching is a workaround that came before Cache-Control support became widely adopted, and basically all responses should explicitly specify a Cache-Control header.

§6 Fresh and stale based on age
S42 Stored HTTP responses have two states: fresh and stale.
S43 The fresh state usually indicates that the response is still valid and can be reused, while the stale state means that the cached response has already expired.
S44 The criterion for determining when a response is fresh and when it is stale is age.
S45 In HTTP, age is the time elapsed since the response was generated.
S46 This is similar to the TTL in other caching mechanisms.

§7 Expires or max-age
S58 In HTTP/1.0, freshness used to be specified by the Expires header.
S59 The Expires header specifies the lifetime of the cache using an explicit time rather than by specifying an elapsed time.
S60 http
S61 However, the time format is difficult to parse, many implementation bugs were found, and it is possible to induce problems by intentionally shifting the system clock; therefore, max-age — for specifying an elapsed time — was adopted for Cache-Control in HTTP/1.1.
S62 If both Expires and Cache-Control: max-age are available, max-age is defined to be preferred.
S63 So it is not necessary to provide Expires now that HTTP/1.1 is widely used.

§8 Vary
S64 The way that responses are distinguished from one another is essentially based on their URLs:
S65 But the contents of responses are not always the same, even if they have the same URL.
S66 Especially when content negotiation is performed, the response from the server can depend on the values of the Accept, Accept-Language, and Accept-Encoding request headers.
S67 For example, for English content returned with an Accept-Language: en header and cached, it is undesirable to then reuse that cached response for requests that have an Accept-Language: ja request header.
S68 In this case, you can cause the responses to be cached separately — based on language — by adding Accept-Language to the value of the Vary header.
S69 http
S70 That causes the cache to be keyed based on a composite of the response URL and the Accept-Language request header — rather than being based just on the response URL.
S71 Also, if you are providing content optimization (for example, for responsive design) based on the user agent, you may be tempted to include User-Agent in the value of the Vary header.
S72 However, the User-Agent request header generally has a very large number of variations, which drastically reduces the chance that the cache will be reused.
S73 So if possible, instead consider a way to vary behavior based on feature detection rather than based on the User-Agent request header.
S74 For applications that employ cookies to prevent others from reusing cached personalized content, you should specify Cache-Control: private instead of specifying a cookie for Vary.

§9 Validation
S75 Stale responses are not immediately discarded.
S76 HTTP has a mechanism to transform a stale response into a fresh one by asking the origin server.
S77 This is called validation, or sometimes, revalidation.
S78 Validation is done by using a conditional request that includes an If-Modified-Since or If-None-Match request header.

S87 Upon receiving that response, the client reverts the stored stale response back to being fresh and can reuse it during the remaining 1 hour.
S88 The server can obtain the modification time from the operating-system file system, which is relatively easy to do for the case of serving static files.
S89 However, there are some problems; for example, the time format is complex and difficult to parse, and distributed servers have difficulty synchronizing file-update times.
S90 To solve such problems, the ETag response header was standardized as an alternative.

§11 ETag/If-None-Match
S91 The value of the ETag response header is an arbitrary value generated by the server.
S92 There are no restrictions on how the server must generate the value, so servers are free to set the value based on whatever means they choose — such as a hash of the body contents or a version number.

S96 http
S97 The server will return 304 Not Modified if the value of the ETag header it determines for the requested resource is the same as the If-None-Match value in the request.
S98 But if the server determines the requested resource should now have a different ETag value, the server will instead respond with a 200 OK and the latest version of the resource.
S99 Note: RFC9110 prefers that servers send both ETag and Last-Modified for a 200 response if possible.
S100 During cache revalidation, if both If-Modified-Since and If-None-Match are present, then If-None-Match takes precedence for the validator.
S101 If you are only considering caching, you may think that Last-Modified is unnecessary.
S102 However, Last-Modified is not just useful for caching; it is a standard HTTP header that is also used by content-management (CMS) systems to display the last-modified time, by crawlers to adjust crawl frequency, and for other various purposes.
S103 So considering the overall HTTP ecosystem, it is better to provide both ETag and Last-Modified.

§12 Force Revalidation
S104 If you do not want a response to be reused, but instead want to always fetch the latest content from the server, you can use the no-cache directive to force validation.
S105 By adding Cache-Control: no-cache to the response along with Last-Modified and ETag — as shown below — the client will receive a 200 OK response if the requested resource has been updated, or will otherwise receive a 304 Not Modified response if the requested resource has not been updated.
S106 http
S107 Note: The no-cache directive (or equivalent, such as max-age=0, must-revalidate) does not guarantee revalidation for history navigations — such as those made using the Back button.
S108 If the back/forward cache (bfcache) is used, the browser restores a snapshot of the page without revalidating.
S109 Even when bfcache is not used, the browser may still serve the cached response without revalidating.
S110 This is allowed by the specification because history navigations are usually treated as restoring a snapshot of a historical session and not a new request for a previously visited page.
S111 It is often stated that the combination of max-age=0 and must-revalidate has the same meaning as no-cache.
S112 http
S113 max-age=0 means that the response is immediately stale, and must-revalidate means that it must not be reused without revalidation once it is stale — so, in combination, the semantics seem to be the same as no-cache.
S114 However, that usage of max-age=0 is a remnant of the fact that many implementations prior to HTTP/1.1 were unable to handle the no-cache directive — and so to deal with that limitation, max-age=0 was used as a workaround.
S115 But now that HTTP/1.1-conformant servers are widely deployed, there's no reason to ever use that max-age=0 and must-revalidate combination — you should instead just use no-cache.

§13 Don't cache
S116 The no-cache directive does not prevent the storing of responses but instead prevents the reuse of responses without revalidation.
S117 If you don't want a response stored in any cache, use no-store.
S118 http
S119 However, in general, a "do not cache" requirement in practice amounts to the following set of circumstances:
S120 Don't want the response stored by anyone other than the specific client, for privacy reasons.
S121 Want to provide up-to-date information always.
S122 Don't know what could happen in outdated implementations.
S123 Under that set of circumstances, no-store is not always the most-appropriate directive.
S124 The following sections look at the circumstances in more detail.

§14 Do not share with others
S125 It would be problematic if a response with personalized content is unexpectedly visible to other users of a cache.
S126 In such a case, using the private directive will cause the personalized response to only be stored with the specific client and not be leaked to any other user of the cache.
S127 http

§15 Provide up-to-date content every time
S128 The no-store directive prevents a response from being stored, but does not delete any already-stored response for the same URL.
S129 In other words, if there is an old response already stored for a particular URL, returning no-store will not prevent the old response from being reused.
S130 However, a no-cache directive will force the client to send a validation request before reusing any stored response.
S131 http
S132 If the server does not support conditional requests, you can force the client to access the server every time and always get the latest response with 200 OK.

§17 What's lost by no-store
S138 You may think adding no-store would be the right way to opt-out of caching.
S139 However, it's not recommended to grant no-store liberally, because you lose many advantages that HTTP and browsers have, including the browser's back/forward cache.
S140 Therefore, to get the advantages of the full feature set of the web platform, prefer the use of no-cache in combination with private.

S168 You may want to overwrite that response once it expired on the server, but there is nothing the server can do once the response is stored — since no more requests reach the server due to caching.
S169 One of the methods mentioned in the specification is to send a request for the same URL with an unsafe method such as POST, but for many clients that is difficult to do.

S171 Otherwise responses will remain in the browser cache until max-age expires, unless the user manually performs a reload, force-reload, or clear-history action.
S172 Caching reduces access to the server, which means that the server loses control of that URL.
S173 If the server does not want to lose control of a URL — for example, in the case that a resource is frequently updated — you should add no-cache so that the server will always receive requests and send the intended responses.

§23 Request collapse
S174 The shared cache is primarily located before the origin server and is intended to reduce traffic to the origin server.
S175 Thus, if multiple identical requests arrive at a shared cache at the same time, the intermediate cache will forward a single request on behalf of itself to the origin, which can then reuse the result for all clients.
S176 This is called request collapse.
S177 Request collapse occurs when requests are arriving at the same time, so even if max-age=0 or no-cache is given in the response, it will be reused.

§24 Common caching patterns
S179 There are many directives in the Cache-Control spec, and it may be difficult to understand all of them.
S180 But most websites can be covered by a combination of a handful of patterns.

§29 More about managed caches
S236 With the method described in previous sections, subresources can be cached for a long time by using cache busting, but main resources (which are usually HTML documents) can't be.
S237 Caching main resources is difficult because, using just standard directives from the HTTP Caching specification, there's no way to actively delete cache contents when content is updated on the server.
S238 However, it is possible by deploying a managed cache such as a CDN or service worker.
S239 For example, a CDN that allows cache purging via an API or dashboard operation would allow for a more aggressive caching strategy by storing the main resource and explicitly purging the relevant cache only when an update occurs on the server.
S240 A service worker could do the same if it could delete the contents in the Cache API when an update occurs on the server.
S241 For more information, see the documentation for your CDN, and consult the service worker documentation.
