SUBJECT "Making cross-origin requests" (under theme "Making a request")
  s3 Whether a request can be made cross-origin or not is determined by the value of the RequestInit.mode option.
  s4 This may take one of three values: cors, same-origin, or no-cors.
  s5 For fetch requests the default value of mode is cors, meaning that if the request is cross-origin then it will use the Cross-Origin Resource Sharing (CORS) mechanism.
  s6 if the request is a simple request, then the request will always be sent, but the server must respond with the correct Access-Control-Allow-Origin header or the browser will not share the response with the caller.
  s7 if the request is not a simple request, then the browser will send a preflighted request to check that the server understands CORS and allows the request, and the real request will not be sent unless the server responds to the preflighted request with the appropriate CORS headers.
  s8 Setting mode to same-origin disallows cross-origin requests completely.
  s9 Setting mode to no-cors disables CORS for cross-origin requests.
  s10 This restricts the headers that may be set, and restricts methods to GET, HEAD, and POST.
  s11 The response is opaque, meaning that its headers and body are not available to JavaScript.

SUBJECT "Including credentials" (under theme "Making a request")
  s12 In the context of the Fetch API, a credential is an extra piece of data sent along with the request that the server may use to authenticate the user.
  s13 By default, credentials are only included in same-origin requests.
  s14 To customize this behavior, as well as to control whether the browser respects any Set-Cookie response headers, set the credentials option, which can take one of the following three values:
  s15 omit: never send credentials in the request or include credentials in the response.
  s16 include: always include credentials, even cross-origin.
  s17 Including credentials in cross-origin requests can make a site vulnerable to CSRF attacks, so even if credentials is set to include, the server must also agree to their inclusion by including the Access-Control-Allow-Credentials header in its response.
  s18 If the request is a simple request, then the request will be sent with credentials, but the server must set the Access-Control-Allow-Credentials and Access-Control-Allow-Origin response headers, or the browser will return a network error to the caller.
  s19 If the request is not a simple request, then the browser will send a preflighted request without credentials, and the server must set the Access-Control-Allow-Credentials and Access-Control-Allow-Origin response headers, or the browser will return a network error to the caller.

THEME "Canceling a request"
  s28 To make a request cancelable, create an AbortController, and assign its AbortSignal to the request's signal property.
  s29 To cancel the request, call the controller's abort() method.
  s30 The fetch() call will reject the promise with an AbortError exception.
  s31 If the request is aborted after the fetch() call has been fulfilled but before the response body has been read, then attempting to read the response body will reject with an AbortError exception.

THEME "Handling the response"
  s33 As soon as the browser has received the response status and headers from the server (and potentially before the response body itself has been received), the promise returned by fetch() is fulfilled with a Response object.

SUBJECT "Checking the response type" (under theme "Handling the response")
  s34 Responses have a type property that can be one of the following:
  s35 basic: the request was a same-origin request.
  s36 cors: the request was a cross-origin CORS request.
  s37 opaque: the request was a cross-origin simple request made with the no-cors mode.
  s38 opaqueredirect: the request set the redirect option to manual, and the server returned a redirect status.
  s39 Basic responses exclude response headers from the Forbidden response header name list.
  s40 CORS responses include only response headers from the CORS-safelisted response header list.
  s41 Opaque responses and opaque redirect responses have a status of 0, an empty header list, and a null body.

SUBJECT "Streaming the response body" (under theme "Handling the response")
  s46 Request and response bodies are actually ReadableStream objects, and whenever you read them, you're streaming the content.
  s47 This is good for memory efficiency, because the browser doesn't have to buffer the entire response in memory before the caller retrieves it using a method like json().
  s48 This also means that the caller can process the content incrementally as it is received.

SUBJECT "Checking response status" (under theme "Handling the response")
  s49 However, if the server responds with an error like 404, then fetch() fulfills with a Response, so we have to check the status before we can read the response body.
  s50 The Response.status property tells us the numerical status code, and the Response.ok property returns true if the status is in the 200 range.

SUBJECT "Checking headers" (under theme "Handling the response")
  s51 Just like the request, the response has a headers property which is a Headers object, and this contains any response headers that are exposed to scripts, subject to the exclusions made based on the response type.
