DOCUMENT: HTTP caching


THEME "no-cache"
  s0 The no-cache directive does not prevent the storing of responses but instead prevents the reuse of responses without revalidation.
  s1 If you don't want a response stored in any cache, use no-store.
  s2 Don't want the response stored by anyone other than the specific client, for privacy reasons.

SUBJECT "no-store" (under theme "no-cache")
  s3 However, it's not recommended to grant no-store liberally, because you lose many advantages that HTTP and browsers have, including the browser's back/forward cache.
  s4 Therefore, to get the advantages of the full feature set of the web platform, prefer the use of no-cache in combination with private.

SUBJECT "Provide up-to-date content every time" (under theme "no-cache")
  s5 The no-store directive prevents a response from being stored, but does not delete any already-stored response for the same URL.
  s6 However, a no-cache directive will force the client to send a validation request before reusing any stored response.
  s7 If the server does not support conditional requests, you can force the client to access the server every time and always get the latest response with 200 OK.

  s10 Request collapse occurs when requests are arriving at the same time, so even if max-age=0 or no-cache is given in the response, it will be reused.

SUBJECT "Do not share with others" (under theme "no-cache")
  s12 It would be problematic if a response with personalized content is unexpectedly visible to other users of a cache.
  s13 In such a case, using the private directive will cause the personalized response to only be stored with the specific client and not be leaked to any other user of the cache.

SUBJECT "Dealing with outdated implementations" (under theme "no-cache")
  s14 It is recommended to use no-cache as an alternative for dealing with such outdated implementations, and it is not a problem if no-cache is given from the beginning, since the server will always receive the request.

THEME "Fresh and stale based on age"
  s15 Stored HTTP responses have two states: fresh and stale.
  s16 The fresh state usually indicates that the response is still valid and can be reused, while the stale state means that the cached response has already expired.
  s17 The criterion for determining when a response is fresh and when it is stale is age.
  s18 In HTTP, age is the time elapsed since the response was generated.
  s19 If the age of the response is less than one week, the response is fresh.
  s20 If the age of the response is more than one week, the response is stale.
  s21 As long as the stored response remains fresh, it will be used to fulfill client requests.

SUBJECT "Heuristic caching" (under theme "Fresh and stale based on age")
  s22 This is called heuristic caching.
  s23 It is heuristically known that content which has not been updated for a full year will not be updated for some time after that.
  s24 Therefore, the client stores this response (despite the lack of max-age) and reuses it for a while.

SUBJECT "Default settings" (under theme "Fresh and stale based on age")
  s25 As mentioned above, the default behavior for caching (that is, for a response without Cache-Control) is not simply "don't cache" but implicit caching according to so-called "heuristic caching".
  s26 To avoid that heuristic caching, it's preferable to explicitly give all responses a default Cache-Control header.

THEME "Validation"
  s29 Stale responses are not immediately discarded.
  s30 HTTP has a mechanism to transform a stale response into a fresh one by asking the origin server.
  s31 This is called validation, or sometimes, revalidation.
  s32 Validation is done by using a conditional request that includes an If-Modified-Since or If-None-Match request header.
  s33 Don't forget to set the Last-Modified and ETag headers, so that you don't have to re-transmit a resource when reloading.
  s34 Cache busting is a technique to make a response cacheable over a long period by changing the URL when the content changes.

SUBJECT "Cache Busting" (under theme "Validation")
  s35 The resources that work best with caching are static immutable files whose contents never change.
  s36 And for resources that do change, it is a common best practice to change the URL each time the content changes, so that the URL unit can be cached for a longer period.
  s37 Therefore, you can serve the JavaScript and CSS with URLs that include a changing part based on a version number or hash value.
  s38 Since the cache distinguishes resources from one another based on their URLs, the cache will not be reused again if the URL changes when a resource is updated.
  s39 With that design, both JavaScript and CSS resources can be cached for a long time.

SUBJECT "ETag/If-None-Match" (under theme "Validation")
  s40 The value of the ETag response header is an arbitrary value generated by the server.
  s41 If that response is stale, the client takes the value of the ETag response header for the cached response, and puts it into the If-None-Match request header, to ask the server if the resource has been modified:
  s42 The server will return 304 Not Modified if the value of the ETag header it determines for the requested resource is the same as the If-None-Match value in the request.
  s43 But if the server determines the requested resource should now have a different ETag value, the server will instead respond with a 200 OK and the latest version of the resource.

SUBJECT "Force Revalidation" (under theme "Validation")
  s44 If you do not want a response to be reused, but instead want to always fetch the latest content from the server, you can use the no-cache directive to force validation.
  s45 By adding Cache-Control: no-cache to the response along with Last-Modified and ETag — as shown below — the client will receive a 200 OK response if the requested resource has been updated, or will otherwise receive a 304 Not Modified response if the requested resource has not been updated.
  s46 Note: The no-cache directive (or equivalent, such as max-age=0, must-revalidate) does not guarantee revalidation for history navigations — such as those made using the Back button.

SUBJECT "Avoiding revalidation" (under theme "Validation")
  s47 Content that never changes should be given a long max-age by using cache busting — that is, by including a version number, hash value, etc., in the request URL.
  s48 To prevent that, the immutable directive can be used to explicitly indicate that revalidation is not required because the content never changes.
  s49 That prevents unnecessary revalidation during reloads.

SUBJECT "If-Modified-Since" (under theme "Validation")
  s50 The server will respond with 304 Not Modified if the content has not changed since the specified time.
  s51 Upon receiving that response, the client reverts the stored stale response back to being fresh and can reuse it during the remaining 1 hour.

SUBJECT "Reload" (under theme "Validation")
  s52 The max-age=0 directive in the request specifies "reuse of responses with an age of 0 or less" — so, in effect, intermediately stored responses are not reused.
  s53 As a result, a request is validated by If-None-Match and If-Modified-Since.

THEME "Expires or max-age"
  s54 The Expires header specifies the lifetime of the cache using an explicit time rather than by specifying an elapsed time.
  s55 However, the time format is difficult to parse, many implementation bugs were found, and it is possible to induce problems by intentionally shifting the system clock; therefore, max-age — for specifying an elapsed time — was adopted for Cache-Control in HTTP/1.1.
  s56 If both Expires and Cache-Control: max-age are available, max-age is defined to be preferred.
  s57 So it is not necessary to provide Expires now that HTTP/1.1 is widely used.

THEME "Types of caches"
  s58 [ESSENTIAL] In the HTTP Caching spec, there are two main types of caches: private caches and shared caches.

SUBJECT "Managed caches" (under theme "Types of caches")
  s59 Managed caches are explicitly deployed by service developers to offload the origin server and to deliver content efficiently.
  s60 The characteristics of managed caches vary depending on the product deployed.
  s61 In most cases, you can control the cache's behavior through the Cache-Control header and your own configuration files or dashboards.
  s62 That means if a managed cache intentionally ignores a no-store directive, there is no need to perceive it as being "non-compliant" with the standard.
  s63 What you should do is, avoid using kitchen-sink headers, but carefully read the documentation of whatever managed-cache mechanism you're using, and ensure you're controlling the cache properly in the ways provided by the mechanism you've chosen to use.
  s64 With the method described in previous sections, subresources can be cached for a long time by using cache busting, but main resources (which are usually HTML documents) can't be.
  s65 Caching main resources is difficult because, using just standard directives from the HTTP Caching specification, there's no way to actively delete cache contents when content is updated on the server.
  s66 However, it is possible by deploying a managed cache such as a CDN or service worker.

SUBJECT "Private caches" (under theme "Types of caches")
  s67 A private cache is a cache tied to a specific client — typically a browser cache.
  s68 Since the stored response is not shared with other clients, a private cache can store a personalized response for that user.
  s69 On the other hand, if personalized contents are stored in a cache other than a private cache, then other users may be able to retrieve those contents — which may cause unintentional information leakage.
  s70 If a response contains personalized content and you want to store the response only in the private cache, you must specify a private directive.
  s71 Personalized contents are usually controlled by cookies, but the presence of a cookie does not always indicate that it is private, and thus a cookie alone does not make the response private.

SUBJECT "Deleting stored responses" (under theme "Types of caches")
  s72 There is no way to delete responses on an intermediate server that have been stored with a long max-age.
  s73 You may want to overwrite that response once it expired on the server, but there is nothing the server can do once the response is stored — since no more requests reach the server due to caching.
  s74 The Clear-Site-Data: cache header and directive value can be used to clear browser caches — but has no effect on intermediate caches.
  s75 Otherwise responses will remain in the browser cache until max-age expires, unless the user manually performs a reload, force-reload, or clear-history action.
  s76 Caching reduces access to the server, which means that the server loses control of that URL.
  s77 If the server does not want to lose control of a URL — for example, in the case that a resource is frequently updated — you should add no-cache so that the server will always receive requests and send the intended responses.

SUBJECT "Shared cache" (under theme "Types of caches")
  s78 The shared cache is located between the client and the server and can store responses that can be shared among users.
  s79 And shared caches can be further sub-classified into proxy caches and managed caches.

THEME "HTTP caching"
  s80 [LEAD] HTTP is designed to cache as much as possible, so even if no Cache-Control is given, responses will get stored and reused if certain conditions are met.

SUBJECT "Main resources" (under theme "HTTP caching")
  s81 Unlike subresources, main resources cannot be cache busted because their URLs can't be decorated in the same way that subresource URLs can be.
  s82 If the following HTML itself is stored, the latest version cannot be displayed even if the content is updated on the server side.

SUBJECT "Vary" (under theme "HTTP caching")
  s85 But the contents of responses are not always the same, even if they have the same URL.
  s86 Especially when content negotiation is performed, the response from the server can depend on the values of the Accept, Accept-Language, and Accept-Encoding request headers.
  s87 In this case, you can cause the responses to be cached separately — based on language — by adding Accept-Language to the value of the Vary header.
  s88 That causes the cache to be keyed based on a composite of the response URL and the Accept-Language request header — rather than being based just on the response URL.
