DOCUMENT: Using the Fetch API

§0 Making a request
S0 To make a request, call fetch(), passing in:
S1 a string containing the URL
S2 an object, such as an instance of URL, which has a stringifier that produces a string containing the URL
S3 a Request instance
S4 optionally, an object containing options to configure the request.
S5 In this section we'll look at some of the most commonly-used options.
S6 To read about all the options that can be given, see the fetch() reference page.

§3 Setting headers
S33 Request headers give the server information about the request: for example, in a POST request, the Content-Type header tells the server the format of the request's body.
S34 To set request headers, assign them to the headers option.
S35 You can pass an object literal here containing header-name: header-value properties:
S36 js
S37 Alternatively, you can construct a Headers object, add headers to that object using Headers.append(), then assign the Headers object to the headers option:
S38 js
S39 Compared to using plain objects, the Headers object provides some additional input sanitization.
S40 For example, it normalizes header names to lowercase, strips leading and trailing whitespace from header values, and prevents certain headers from being set.
S41 Many headers are set automatically by the browser and can't be set by a script: these are called Forbidden request headers.
S42 If the mode option is set to no-cors, then the set of permitted headers is further restricted.

§5 Making cross-origin requests
S47 Whether a request can be made cross-origin or not is determined by the value of the RequestInit.mode option.
S48 This may take one of three values: cors, same-origin, or no-cors.
S49 For fetch requests the default value of mode is cors, meaning that if the request is cross-origin then it will use the Cross-Origin Resource Sharing (CORS) mechanism.
S50 This means that:
S51 if the request is a simple request, then the request will always be sent, but the server must respond with the correct Access-Control-Allow-Origin header or the browser will not share the response with the caller.
S52 if the request is not a simple request, then the browser will send a preflighted request to check that the server understands CORS and allows the request, and the real request will not be sent unless the server responds to the preflighted request with the appropriate CORS headers.
S53 Setting mode to same-origin disallows cross-origin requests completely.
S54 Setting mode to no-cors disables CORS for cross-origin requests.
S55 This restricts the headers that may be set, and restricts methods to GET, HEAD, and POST.
S56 The response is opaque, meaning that its headers and body are not available to JavaScript.
S57 Most of the time a website should not use no-cors: the main application of it is for certain service worker use cases.
S58 See the reference documentation for RequestInit.mode for more details.

§6 Including credentials
S59 In the context of the Fetch API, a credential is an extra piece of data sent along with the request that the server may use to authenticate the user.
S60 All the following items are considered to be credentials:
S61 HTTP cookies
S62 TLS client certificates
S63 The Authorization and Proxy-Authorization headers.
S64 By default, credentials are only included in same-origin requests.
S65 To customize this behavior, as well as to control whether the browser respects any Set-Cookie response headers, set the credentials option, which can take one of the following three values:
S66 omit: never send credentials in the request or include credentials in the response.
S67 same-origin (the default): only send and include credentials for same-origin requests.
S68 include: always include credentials, even cross-origin.
S69 Note that if a cookie's SameSite attribute is set to Strict or Lax, then the cookie will not be sent cross-site, even if credentials is set to include.
S70 Including credentials in cross-origin requests can make a site vulnerable to CSRF attacks, so even if credentials is set to include, the server must also agree to their inclusion by including the Access-Control-Allow-Credentials header in its response.
S71 Additionally, in this situation the server must explicitly specify the client's origin in the Access-Control-Allow-Origin response header (that is, * is not allowed).
S72 This means that if credentials is set to include and the request is cross-origin, then:
S73 If the request is a simple request, then the request will be sent with credentials, but the server must set the Access-Control-Allow-Credentials and Access-Control-Allow-Origin response headers, or the browser will return a network error to the caller.
S74 If the server does set the correct headers, then the response, including credentials, will be delivered to the caller.
S75 If the request is not a simple request, then the browser will send a preflighted request without credentials, and the server must set the Access-Control-Allow-Credentials and Access-Control-Allow-Origin response headers, or the browser will return a network error to the caller.
S76 If the server does set the correct headers, then the browser will follow up with the real request, including credentials, and will deliver the real response, including credentials, to the caller.

§9 Handling the response
S91 As soon as the browser has received the response status and headers from the server (and potentially before the response body itself has been received), the promise returned by fetch() is fulfilled with a Response object.

§10 Checking response status
S92 The promise returned by fetch() will reject on some errors, such as a network error or a bad scheme.
S93 However, if the server responds with an error like 404, then fetch() fulfills with a Response, so we have to check the status before we can read the response body.
S94 The Response.status property tells us the numerical status code, and the Response.ok property returns true if the status is in the 200 range.

§11 Checking the response type
S97 Responses have a type property that can be one of the following:
S98 basic: the request was a same-origin request.
S99 cors: the request was a cross-origin CORS request.
S100 opaque: the request was a cross-origin simple request made with the no-cors mode.
S101 opaqueredirect: the request set the redirect option to manual, and the server returned a redirect status.
S102 The type determines the possible contents of the response, as follows:
S103 Basic responses exclude response headers from the Forbidden response header name list.
S104 CORS responses include only response headers from the CORS-safelisted response header list.
S105 Opaque responses and opaque redirect responses have a status of 0, an empty header list, and a null body.
