# HTTP caching

## Types of caches

{2}In the HTTP Caching spec, there are two main types of caches: private caches and shared caches.

## Private caches

{1}A private cache is a cache tied to a specific client — typically a browser cache. {1}Since the stored response is not shared with other clients, a private cache can store a personalized response for that user.

{1}On the other hand, if personalized contents are stored in a cache other than a private cache, then other users may be able to retrieve those contents — which may cause unintentional information leakage.

{2}If a response contains personalized content and you want to store the response only in the private cache, you must specify a private directive.

{0}http

Cache-Control: private

{1}Personalized contents are usually controlled by cookies, but the presence of a cookie does not always indicate that it is private, and thus a cookie alone does not make the response private.

## Shared cache

{2}The shared cache is located between the client and the server and can store responses that can be shared among users. {1}And shared caches can be further sub-classified into proxy caches and managed caches.

## Proxy caches

{1}In addition to the function of access control, some proxies implement caching to reduce traffic out of the network. {0}This is usually not managed by the service developer, so it must be controlled by appropriate HTTP headers and so on. {0}However, in the past, outdated proxy-cache implementations — such as implementations that do not properly understand the HTTP Caching standard — have often caused problems for developers.

{0}Kitchen-sink headers like the following are used to try to work around "old and not updated proxy cache" implementations that do not understand current HTTP Caching spec directives like no-store.

{0}http

Cache-Control: no-store, no-cache, max-age=0, must-revalidate, proxy-revalidate

{1}However, in recent years, as HTTPS has become more common and client/server communication has become encrypted, proxy caches in the path can only tunnel a response and can't behave as a cache, in many cases. {0}So in that scenario, there is no need to worry about outdated proxy cache implementations that cannot even see the response.

{0}On the other hand, if a TLS bridge proxy decrypts all communications in a person-in-the-middle manner by installing a certificate from a CA (certificate authority) managed by the organization on the PC, and performs access control, etc. — it is possible to see the contents of the response and cache it. {0}However, since CT (certificate transparency) has become widespread in recent years, and some browsers only allow certificates issued with an SCT (signed certificate timestamp), this method requires the application of an enterprise policy. {0}In such a controlled environment, there is no need to worry about the proxy cache being "out of date and not updated".

## Managed caches

{2}Managed caches are explicitly deployed by service developers to offload the origin server and to deliver content efficiently. {1}Examples include reverse proxies, CDNs, and service workers in combination with the Cache API.

{0}The characteristics of managed caches vary depending on the product deployed. {1}In most cases, you can control the cache's behavior through the Cache-Control header and your own configuration files or dashboards.

{1}For example, the HTTP Caching specification essentially does not define a way to explicitly delete a cache — but with a managed cache, the stored response can be deleted at any time through dashboard operations, API calls, restarts, and so on. {1}That allows for a more proactive caching strategy.

{0}It is also possible to ignore the standard HTTP Caching spec protocols in favor of explicit manipulation. {0}For example, the following can be specified to opt-out of a private cache or proxy cache, while using your own strategy to cache only in a managed cache.

{0}http

Cache-Control: no-store

{0}For example, Varnish Cache uses VCL (Varnish Configuration Language, a type of DSL) logic to handle cache storage, while service workers in combination with the Cache API allow you to create that logic in JavaScript.

{1}That means if a managed cache intentionally ignores a no-store directive, there is no need to perceive it as being "non-compliant" with the standard. {2}What you should do is, avoid using kitchen-sink headers, but carefully read the documentation of whatever managed-cache mechanism you're using, and ensure you're controlling the cache properly in the ways provided by the mechanism you've chosen to use.

{0}Note that some CDNs provide their own headers that are effective only for that CDN (for example, Surrogate-Control). {0}Currently, work is underway to define a CDN-Cache-Control header to standardize those.

## Heuristic caching

{2}HTTP is designed to cache as much as possible, so even if no Cache-Control is given, responses will get stored and reused if certain conditions are met. {1}This is called heuristic caching.

{0}For example, take the following response. {0}This response was last updated 1 year ago.

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT Last-Modified: Tue, 22 Feb 2021 22:22:22 GMT <!doctype html> …

{1}It is heuristically known that content which has not been updated for a full year will not be updated for some time after that. {1}Therefore, the client stores this response (despite the lack of max-age) and reuses it for a while. {1}How long to reuse is up to the implementation, but the specification recommends about 10% (in this case 0.1 year) of the time after storing.

{3*}Heuristic caching is a workaround that came before Cache-Control support became widely adopted, and basically all responses should explicitly specify a Cache-Control header.

## Fresh and stale based on age

{2}Stored HTTP responses have two states: fresh and stale. {1}The fresh state usually indicates that the response is still valid and can be reused, while the stale state means that the cached response has already expired.

{2}The criterion for determining when a response is fresh and when it is stale is age. {2}In HTTP, age is the time elapsed since the response was generated. {0}This is similar to the TTL in other caching mechanisms.

{0}Take the following example response (604800 seconds is one week):

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT Cache-Control: max-age=604800 <!doctype html> …

{1}The cache that stored the example response calculates the time elapsed since the response was generated and uses the result as the response's age.

{0}For the example response, the meaning of max-age is the following:

- {1}If the age of the response is less than one week, the response is fresh.

- {1}If the age of the response is more than one week, the response is stale.

{1}As long as the stored response remains fresh, it will be used to fulfill client requests.

{0}When a response is stored in a shared cache, it is possible to tell the client the age of the response. {0}Continuing with the example, if the shared cache stored the response for one day, the shared cache would send the following response to subsequent client requests.

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT Cache-Control: max-age=604800 Age: 86400 <!doctype html> …

{1}The client which receives that response will find it to be fresh for the remaining 518400 seconds, the difference between the response's max-age and Age.

## Expires or max-age

{1}In HTTP/1.0, freshness used to be specified by the Expires header.

{0}The Expires header specifies the lifetime of the cache using an explicit time rather than by specifying an elapsed time.

{0}http

Expires: Tue, 28 Feb 2022 22:22:22 GMT

{1}However, the time format is difficult to parse, many implementation bugs were found, and it is possible to induce problems by intentionally shifting the system clock; therefore, max-age — for specifying an elapsed time — was adopted for Cache-Control in HTTP/1.1.

{2}If both Expires and Cache-Control: max-age are available, max-age is defined to be preferred. {0}So it is not necessary to provide Expires now that HTTP/1.1 is widely used.

## Vary

{0}The way that responses are distinguished from one another is essentially based on their URLs:

{2}But the contents of responses are not always the same, even if they have the same URL. {1}Especially when content negotiation is performed, the response from the server can depend on the values of the Accept, Accept-Language, and Accept-Encoding request headers.

{0}For example, for English content returned with an Accept-Language: en header and cached, it is undesirable to then reuse that cached response for requests that have an Accept-Language: ja request header. {2}In this case, you can cause the responses to be cached separately — based on language — by adding Accept-Language to the value of the Vary header.

{0}http

Vary: Accept-Language

{1}That causes the cache to be keyed based on a composite of the response URL and the Accept-Language request header — rather than being based just on the response URL.

{0}Also, if you are providing content optimization (for example, for responsive design) based on the user agent, you may be tempted to include User-Agent in the value of the Vary header. {1}However, the User-Agent request header generally has a very large number of variations, which drastically reduces the chance that the cache will be reused. {1}So if possible, instead consider a way to vary behavior based on feature detection rather than based on the User-Agent request header.

{1}For applications that employ cookies to prevent others from reusing cached personalized content, you should specify Cache-Control: private instead of specifying a cookie for Vary.

## Validation

{1}Stale responses are not immediately discarded. {3*}HTTP has a mechanism to transform a stale response into a fresh one by asking the origin server. {1}This is called validation, or sometimes, revalidation.

{2}Validation is done by using a conditional request that includes an If-Modified-Since or If-None-Match request header.

## If-Modified-Since

{0}The following response was generated at 22:22:22 and has a max-age of 1 hour, so you know that it is fresh until 23:22:22.

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT Last-Modified: Tue, 22 Feb 2022 22:00:00 GMT Cache-Control: max-age=3600 <!doctype html> …

{0}At 23:22:22, the response becomes stale and the cache cannot be reused. {0}So the request below shows a client sending a request with an If-Modified-Since request header, to ask the server if there have been any changes made since the specified time.

{0}http

GET /index.html HTTP/1.1 Host: example.com Accept: text/html If-Modified-Since: Tue, 22 Feb 2022 22:00:00 GMT

{2}The server will respond with 304 Not Modified if the content has not changed since the specified time.

{1}Since this response only indicates "no change", there is no response body — there's just a status code — so the transfer size is extremely small.

{0}http

HTTP/1.1 304 Not Modified Content-Type: text/html Date: Tue, 22 Feb 2022 23:22:22 GMT Last-Modified: Tue, 22 Feb 2022 22:00:00 GMT Cache-Control: max-age=3600

{2}Upon receiving that response, the client reverts the stored stale response back to being fresh and can reuse it during the remaining 1 hour.

{1}The server can obtain the modification time from the operating-system file system, which is relatively easy to do for the case of serving static files. {1}However, there are some problems; for example, the time format is complex and difficult to parse, and distributed servers have difficulty synchronizing file-update times.

{1}To solve such problems, the ETag response header was standardized as an alternative.

## ETag/If-None-Match

{2}The value of the ETag response header is an arbitrary value generated by the server. {1}There are no restrictions on how the server must generate the value, so servers are free to set the value based on whatever means they choose — such as a hash of the body contents or a version number.

{0}As an example, if a hash value is used for the ETag header and the hash value of the index.html resource is 33a64df5, the response will be as follows:

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT ETag: "33a64df5" Cache-Control: max-age=3600 <!doctype html> …

{1}If that response is stale, the client takes the value of the ETag response header for the cached response, and puts it into the If-None-Match request header, to ask the server if the resource has been modified:

{0}http

GET /index.html HTTP/1.1 Host: example.com Accept: text/html If-None-Match: "33a64df5"

{2}The server will return 304 Not Modified if the value of the ETag header it determines for the requested resource is the same as the If-None-Match value in the request.

{1}But if the server determines the requested resource should now have a different ETag value, the server will instead respond with a 200 OK and the latest version of the resource.

{1}Note: RFC9110 prefers that servers send both ETag and Last-Modified for a 200 response if possible. {1}During cache revalidation, if both If-Modified-Since and If-None-Match are present, then If-None-Match takes precedence for the validator. {0}If you are only considering caching, you may think that Last-Modified is unnecessary. {1}However, Last-Modified is not just useful for caching; it is a standard HTTP header that is also used by content-management (CMS) systems to display the last-modified time, by crawlers to adjust crawl frequency, and for other various purposes. {1}So considering the overall HTTP ecosystem, it is better to provide both ETag and Last-Modified.

## Force Revalidation

{2}If you do not want a response to be reused, but instead want to always fetch the latest content from the server, you can use the no-cache directive to force validation.

{1}By adding Cache-Control: no-cache to the response along with Last-Modified and ETag — as shown below — the client will receive a 200 OK response if the requested resource has been updated, or will otherwise receive a 304 Not Modified response if the requested resource has not been updated.

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT Last-Modified: Tue, 22 Feb 2022 22:00:00 GMT ETag: "deadbeef" Cache-Control: no-cache <!doctype html> …

{1}Note: The no-cache directive (or equivalent, such as max-age=0, must-revalidate) does not guarantee revalidation for history navigations — such as those made using the Back button. {0}If the back/forward cache (bfcache) is used, the browser restores a snapshot of the page without revalidating. {0}Even when bfcache is not used, the browser may still serve the cached response without revalidating. {0}This is allowed by the specification because history navigations are usually treated as restoring a snapshot of a historical session and not a new request for a previously visited page.

{0}It is often stated that the combination of max-age=0 and must-revalidate has the same meaning as no-cache.

{0}http

Cache-Control: max-age=0, must-revalidate

{1}max-age=0 means that the response is immediately stale, and must-revalidate means that it must not be reused without revalidation once it is stale — so, in combination, the semantics seem to be the same as no-cache.

{1}However, that usage of max-age=0 is a remnant of the fact that many implementations prior to HTTP/1.1 were unable to handle the no-cache directive — and so to deal with that limitation, max-age=0 was used as a workaround.

{2}But now that HTTP/1.1-conformant servers are widely deployed, there's no reason to ever use that max-age=0 and must-revalidate combination — you should instead just use no-cache.

## Don't cache

{3*}The no-cache directive does not prevent the storing of responses but instead prevents the reuse of responses without revalidation.

{2}If you don't want a response stored in any cache, use no-store.

{0}http

Cache-Control: no-store

{0}However, in general, a "do not cache" requirement in practice amounts to the following set of circumstances:

- {0}Don't want the response stored by anyone other than the specific client, for privacy reasons.

- {0}Want to provide up-to-date information always.

- {0}Don't know what could happen in outdated implementations.

{1}Under that set of circumstances, no-store is not always the most-appropriate directive.

{0}The following sections look at the circumstances in more detail.

{1}It would be problematic if a response with personalized content is unexpectedly visible to other users of a cache.

{2}In such a case, using the private directive will cause the personalized response to only be stored with the specific client and not be leaked to any other user of the cache.

{0}http

Cache-Control: private

## Provide up-to-date content every time

{2}The no-store directive prevents a response from being stored, but does not delete any already-stored response for the same URL.

{1}In other words, if there is an old response already stored for a particular URL, returning no-store will not prevent the old response from being reused.

{2}However, a no-cache directive will force the client to send a validation request before reusing any stored response.

{0}http

Cache-Control: no-cache

{1}If the server does not support conditional requests, you can force the client to access the server every time and always get the latest response with 200 OK.

## Dealing with outdated implementations

{0}As a workaround for outdated implementations that ignore no-store, you may see kitchen-sink headers such as the following being used.

{0}http

Cache-Control: no-store, no-cache, max-age=0, must-revalidate, proxy-revalidate

{2}It is recommended to use no-cache as an alternative for dealing with such outdated implementations, and it is not a problem if no-cache is given from the beginning, since the server will always receive the request.

{1}If it is the shared cache that you are concerned about, you can make sure to prevent unintended caching by also adding private:

{0}http

Cache-Control: no-cache, private

## What's lost by no-store

{0}You may think adding no-store would be the right way to opt-out of caching.

{2}However, it's not recommended to grant no-store liberally, because you lose many advantages that HTTP and browsers have, including the browser's back/forward cache.

{3}Therefore, to get the advantages of the full feature set of the web platform, prefer the use of no-cache in combination with private.

## Reload and force reload

{1}Validation can be performed for requests as well as responses.

{1}The reload and force reload actions are common examples of validation performed from the browser side.

## Reload

{0}For recovering from window corruption or updating to the latest version of the resource, browsers provide a reload function for users.

{0}A simplified view of the HTTP request sent during a browser reload looks as follows:

{0}http

GET / HTTP/1.1 Host: example.com Cache-Control: max-age=0 If-None-Match: "deadbeef" If-Modified-Since: Tue, 22 Feb 2022 20:20:20 GMT

{0}(The requests from Chrome, Edge, and Firefox look very much like the above; the requests from Safari will look a bit different.)

{1}The max-age=0 directive in the request specifies "reuse of responses with an age of 0 or less" — so, in effect, intermediately stored responses are not reused.

{1}As a result, a request is validated by If-None-Match and If-Modified-Since.

{0}That behavior is also defined in the Fetch standard and can be reproduced in JavaScript by calling fetch() with the cache mode set to no-cache (note that reload is not the right mode for this case):

{0}js

// Note: "reload" is not the right mode for a normal reload; "no-cache" is fetch("/", { cache: "no-cache" });

## Force reload

{1}Browsers use max-age=0 during reloads for backward-compatibility reasons — because many outdated implementations prior to HTTP/1.1 did not understand no-cache. {1}But no-cache is fine now in this use case, and force reload is an additional way to bypass cached responses.

{0}The HTTP Request during a browser force reload looks as follows:

{0}http

GET / HTTP/1.1 Host: example.com Pragma: no-cache Cache-Control: no-cache

{0}(The requests from Chrome, Edge, and Firefox look very much like the above; the requests from Safari will look a bit different.)

{1}Since that's not a conditional request with no-cache, you can be sure you'll get a 200 OK from the origin server.

{0}That behavior is also defined in the Fetch standard and can be reproduced in JavaScript by calling fetch() with the cache mode set to reload (note that it's not force-reload):

{0}js

// Note: "reload" — rather than "no-cache" — is the right mode for a "force reload" fetch("/", { cache: "reload" });

## Avoiding revalidation

{2}Content that never changes should be given a long max-age by using cache busting — that is, by including a version number, hash value, etc., in the request URL.

{1}However, when the user reloads, a revalidation request is sent even though the server knows that the content is immutable.

{2}To prevent that, the immutable directive can be used to explicitly indicate that revalidation is not required because the content never changes.

{0}http

Cache-Control: max-age=31536000, immutable

{0}That prevents unnecessary revalidation during reloads.

{0}Note that, instead of implementing that directive, Chrome has changed its implementation so that revalidation is not performed during reloads for subresources.

## Deleting stored responses

{2}There is no way to delete responses on an intermediate server that have been stored with a long max-age.

{0}Imagine that the following response from https://example.com/ was stored.

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Cache-Control: max-age=31536000 <!doctype html> …

{1}You may want to overwrite that response once it expired on the server, but there is nothing the server can do once the response is stored — since no more requests reach the server due to caching.

{0}One of the methods mentioned in the specification is to send a request for the same URL with an unsafe method such as POST, but for many clients that is difficult to do.

{1}The Clear-Site-Data: cache header and directive value can be used to clear browser caches — but has no effect on intermediate caches. {1}Otherwise responses will remain in the browser cache until max-age expires, unless the user manually performs a reload, force-reload, or clear-history action.

{2}Caching reduces access to the server, which means that the server loses control of that URL. {1}If the server does not want to lose control of a URL — for example, in the case that a resource is frequently updated — you should add no-cache so that the server will always receive requests and send the intended responses.

## Request collapse

{1}The shared cache is primarily located before the origin server and is intended to reduce traffic to the origin server.

{2}Thus, if multiple identical requests arrive at a shared cache at the same time, the intermediate cache will forward a single request on behalf of itself to the origin, which can then reuse the result for all clients. {1}This is called request collapse.

{1}Request collapse occurs when requests are arriving at the same time, so even if max-age=0 or no-cache is given in the response, it will be reused.

## Common caching patterns

{0}There are many directives in the Cache-Control spec, and it may be difficult to understand all of them. {1}But most websites can be covered by a combination of a handful of patterns.

{0}This section describes the common patterns in designing caches.

## Default settings

{1}As mentioned above, the default behavior for caching (that is, for a response without Cache-Control) is not simply "don't cache" but implicit caching according to so-called "heuristic caching".

{1}To avoid that heuristic caching, it's preferable to explicitly give all responses a default Cache-Control header.

{2}To ensure that by default the latest versions of resources will always be transferred, it's common practice to make the default Cache-Control value include no-cache:

{0}http

Cache-Control: no-cache

{2}In addition, if the service implements cookies or other login methods, and the content is personalized for each user, private must be given too, to prevent sharing with other users:

{0}http

Cache-Control: no-cache, private

## Cache Busting

{2}The resources that work best with caching are static immutable files whose contents never change. {3*^}And for resources that do change, it is a common best practice to change the URL each time the content changes, so that the URL unit can be cached for a longer period.

{0}As an example, consider the following HTML:

{0}html

<script src="bundle.js"></script> <link rel="stylesheet" href="build.css" /> <body>   hello </body>

{0}In modern web development, JavaScript and CSS resources are frequently updated as development progresses. {0}Also, if the versions of JavaScript and CSS resources that a client uses are out of sync, the display will break.

{1}So the HTML above makes it difficult to cache bundle.js and build.css with max-age.

{2}Therefore, you can serve the JavaScript and CSS with URLs that include a changing part based on a version number or hash value. {0}Some of the ways to do that are shown below.

# version in filename bundle.v123.js # version in query bundle.js?v=123 # hash in filename bundle.YsAIAAAA-QG4G6kCMAMBAAAAAAAoK.js # hash in query bundle.js?v=YsAIAAAA-QG4G6kCMAMBAAAAAAAoK

{1}Since the cache distinguishes resources from one another based on their URLs, the cache will not be reused again if the URL changes when a resource is updated.

{0}html

<script src="bundle.v123.js"></script> <link rel="stylesheet" href="build.v123.css" /> <body>   hello </body>

{1}With that design, both JavaScript and CSS resources can be cached for a long time. {0}So how long should max-age be set to? {0}The QPACK specification provides an answer to that question.

{0}QPACK is a standard for compressing HTTP header fields, with tables of commonly-used field values defined.

{0}Some commonly-used cache-header values are shown below.

36 cache-control max-age=0 37 cache-control max-age=604800 38 cache-control max-age=2592000 39 cache-control no-cache 40 cache-control no-store 41 cache-control public, max-age=31536000

{0}If you select one of those numbered options, you can compress values in 1 byte when transferred via HTTP3.

{0}Numbers 37, 38, and 41 are for periods of one week, one month, and one year.

{1}Because the cache removes old entries when new entries are saved, the probability that a stored response still exists after one week is not that high — even if max-age is set to 1 week. {1}Therefore, in practice, it does not make much difference which one you choose.

{0}Note that number 41 has the longest max-age (1 year), but with public.

{1}The public value has the effect of making the response storable even if the Authorization header is present.

{1}Note: The public directive should only be used if there is a need to store the response when the Authorization header is set. {0}It is not required otherwise, because a response will be stored in the shared cache as long as max-age is given.

{1}So if the response is personalized with basic authentication, the presence of public may cause problems. {0}If you are concerned about that, you can choose the second-longest value, 38 (1 month).

{0}http

# response for bundle.v123.js # If you never personalize responses via Authorization Cache-Control: public, max-age=31536000 # If you can't be certain Cache-Control: max-age=2592000

## Validation

{1}Don't forget to set the Last-Modified and ETag headers, so that you don't have to re-transmit a resource when reloading. {0}It's easy to generate those headers for pre-built static files.

{0}The ETag value here may be a hash of the file.

{0}http

# response for bundle.v123.js Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT ETag: "YsAIAAAA-QG4G6kCMAMBAAAAAAAoK"

{1}In addition, immutable can be added to prevent validation on reload.

{0}The combined result is shown below.

{0}http

# bundle.v123.js HTTP/1.1 200 OK Content-Type: text/javascript Content-Length: 1024 Cache-Control: public, max-age=31536000, immutable Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT ETag: "YsAIAAAA-QG4G6kCMAMBAAAAAAAoK"

{3}Cache busting is a technique to make a response cacheable over a long period by changing the URL when the content changes. {1}The technique can be applied to all subresources, such as images.

{0}Note: When evaluating the use of immutable and QPACK: If you're concerned that immutable changes the predefined value provided by QPACK, consider that in this case, the immutable part can be encoded separately by splitting the Cache-Control value into two lines — though this is dependent on the encoding algorithm a particular QPACK implementation uses.

{0}http

Cache-Control: public, max-age=31536000 Cache-Control: immutable

## Main resources

{2}Unlike subresources, main resources cannot be cache busted because their URLs can't be decorated in the same way that subresource URLs can be.

{1}If the following HTML itself is stored, the latest version cannot be displayed even if the content is updated on the server side.

{0}html

<script src="bundle.v123.js"></script> <link rel="stylesheet" href="build.v123.css" /> <body>   hello </body>

{2}For that case, no-cache would be appropriate — rather than no-store — since we don't want to store HTML, but instead just want it to always be up-to-date.

{1}Furthermore, adding Last-Modified and ETag will allow clients to send conditional requests, and a 304 Not Modified can be returned if there have been no updates to the HTML:

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Cache-Control: no-cache Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT ETag: "AAPuIbAOdvAGEETbgAAAAAAABAAE"

{1}That setting is appropriate for non-personalized HTML, but for a response that gets personalized using cookies — for example, after a login — don't forget to also specify private:

{0}http

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Cache-Control: no-cache, private Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT ETag: "AAPuIbAOdvAGEETbgAAAAAAABAAE" Set-Cookie: __Host-SID=AHNtAyt3fvJrUL5g5tnGwER; Secure; Path=/; HttpOnly

{1}The same can be used for favicon.ico, manifest.json, .well-known, and API endpoints whose URLs cannot be changed using cache busting.

{2}Most web content can be covered by a combination of the two patterns described above.

## More about managed caches

{1}With the method described in previous sections, subresources can be cached for a long time by using cache busting, but main resources (which are usually HTML documents) can't be.

{1}Caching main resources is difficult because, using just standard directives from the HTTP Caching specification, there's no way to actively delete cache contents when content is updated on the server.

{2}However, it is possible by deploying a managed cache such as a CDN or service worker.

{1}For example, a CDN that allows cache purging via an API or dashboard operation would allow for a more aggressive caching strategy by storing the main resource and explicitly purging the relevant cache only when an update occurs on the server.

{0}A service worker could do the same if it could delete the contents in the Cache API when an update occurs on the server.

{0}For more information, see the documentation for your CDN, and consult the service worker documentation.
